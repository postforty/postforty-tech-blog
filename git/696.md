# Git 실무 핵심 가이드: 브랜치 관리부터 커밋 복구 및 리셋까지

형상 관리 도구로 Git을 사용하다 보면 브랜치 이름을 잘못 생성하거나, 원격 브랜치와의 추적(Upstream) 연결이 끊어지거나, 잘못 커밋한 내용을 과거 시점으로 되돌려야 하는 위기 상황에 직면한다. 

GUI 도구는 직관적이지만 예기치 않은 오류가 발생했을 때 문제의 근본 원인을 파악하고 정밀하게 수습하기 어렵다. 터미널 기반의 핵심 Git 명령어를 명확히 이해하고 있으면 예기치 않은 히스토리 꼬임 현상도 안전하게 복구할 수 있다.

- **테스트 환경**: Git 2.23 이상 (최신 권장 명령어 `git switch` 지원)
- **운영체제**: macOS / Linux / Windows PowerShell 공통

---

## 1. 브랜치 생성과 이름 변경 및 원격 동기화

프로젝트 진행 중 브랜치 명명 규칙이 변경되거나 오타가 발생했을 때 로컬 브랜치 이름을 변경하고 원격 저장소와 동기화해야 한다.

### 로컬 브랜치 이름 변경

브랜치 이름을 변경할 때는 `-m`(`--move`) 옵션을 사용한다. 이 옵션은 브랜치 참조(Reference)뿐만 아니라 작업 기록인 Reflog까지 안전하게 함께 이동시킨다.

현재 체크아웃되어 있는 브랜치의 이름을 변경하는 명령이다.

```sh
git branch -m 변경할_새_이름
```

현재 위치가 아닌 다른 브랜치의 이름을 변경할 때는 기존 이름과 새 이름을 순서대로 지정한다.

```sh
git branch -m 기존_이름 변경할_새_이름
```

### 원격 저장소 동기화 및 기존 브랜치 삭제

로컬 브랜치 이름을 변경하더라도 원격 저장소에는 자동으로 반영되지 않는다. 새 브랜치를 원격에 업스트림으로 설정하여 푸시한 뒤, 과거 이름의 원격 브랜치를 명시적으로 삭제해야 한다.

```sh
# 새 브랜치를 원격 저장소에 푸시하고 기본 추적 브랜치로 설정
git push -u origin 변경할_새_이름

# 원격 저장소에 남아 있는 기존 이름의 브랜치 삭제
git push origin --delete 기존_이름
```

`-u`(`--set-upstream`) 옵션은 로컬 브랜치가 지정한 원격 브랜치를 지속적으로 추적하도록 기본 업스트림으로 등록한다. 이후에는 브랜치 명시 없이 `git push` 또는 `git pull`만으로 작업이 가능하다.

### 원격 브랜치를 기반으로 새 로컬 브랜치 생성 및 이동

원격 브랜치에서 분기하여 새로운 로컬 브랜치를 생성하고 즉시 이동할 때는 과거의 `checkout` 대신 Git 2.23부터 분리 도입된 `switch` 명령어 사용을 권장한다.

```sh
# 최신 권장 방식: 새로운 브랜치를 생성(-c)하고 즉시 이동
git switch -c 새_브랜치_이름 origin/원격_브랜치_이름

# 기존 방식: 생성(-b)과 체크아웃을 동시에 수행
git checkout -b 새_브랜치_이름 origin/원격_브랜치_이름
```

## 2. 브랜치 정리: 안전한 삭제와 강제 삭제

기능 개발이 완료되어 메인 브랜치에 병합되었거나 버려진 브랜치는 주기적으로 정리하여 저장소를 깔끔하게 유지해야 한다.

| 명령어 | 옵션 | 동작 특성 |
| :--- | :--- | :--- |
| `git branch -d` | `--delete` | 대상 브랜치가 상위 브랜치에 병합(Merge)되었을 때만 삭제 허용 |
| `git branch -D` | `--delete --force` | 병합 여부와 관계없이 브랜치를 강제로 즉시 삭제 |

### 안전 삭제 (`-d`)

머지가 완료된 브랜치를 삭제할 때 사용한다. 만약 대상 브랜치에 병합되지 않은 커밋이 존재한다면 Git은 경고 메시지와 함께 삭제를 거부하여 코드 유실을 방지한다.

```sh
git branch -d 삭제할_브랜치_이름
```

### 강제 삭제 (`-D`)

실험적인 기능을 구현하다가 완전히 폐기하기로 결정한 브랜치처럼, 병합하지 않고 폐기할 브랜치는 대문자 `-D` 옵션으로 강제 삭제한다.

```sh
git branch -D 삭제할_브랜치_이름
```

## 3. 커밋 히스토리 및 작업 이력 추적

히스토리를 파악할 때는 불필요한 메타데이터를 최소화하고 변경 사항의 핵심을 빠르게 확인하는 필터링 명령어가 필수적이다.

### 커밋 로그 간략 조회 및 상세 확인

```sh
# 커밋 해시와 메시지를 한 줄로 요약하여 출력
git log --oneline

# 가장 최근 커밋 1개의 상세 정보(작성자, 날짜, 메시지)만 조회
git log -1

# 가장 최근 커밋에서 발생한 실제 코드 변경 차이점(Diff) 조회
git show
```

특정 브랜치만 필터링하여 확인하거나 원격 브랜치의 변경 상황을 단독으로 검토할 수도 있다.

```sh
# 로컬의 특정 브랜치 로그 확인
git log 특정_브랜치_이름

# 원격 브랜치에 반영된 커밋 로그만 확인
git log origin/원격_브랜치_이름
```

### 모든 조작 기록 추적: `git reflog`

`git log`는 유효한 커밋 그래프만을 탐색하지만, `git reflog`(Reference Log)는 저장소 내에서 `HEAD` 포인터가 이동했던 모든 이력을 시간순으로 기록한다. 

실수로 브랜치를 잘못 삭제했거나 `git reset --hard`로 커밋을 날렸을 때 복구할 기준 해시값을 찾는 핵심 안전망 역할을 한다.

```sh
git reflog
```

## 4. 원격 추적 관리와 커밋 되돌리기 (Reset)

원격 저장소와의 연결 상태가 꼬였거나 잘못 반영된 로컬 커밋을 초기화해야 할 때 사용하는 고급 명령어이다.

### 업스트림(Upstream) 상태 점검 및 재설정

현재 로컬 브랜치가 어떤 원격 브랜치와 연결되어 있는지, 커밋 차이는 얼마나 나는지 한눈에 파악할 수 있다.

```sh
# 로컬 브랜치 목록과 연동된 원격 브랜치 상태 상세 확인
git branch -vv

# 현재 로컬 브랜치의 원격 추적 대상(Upstream)을 새롭게 재지정
git branch -u origin/올바른_원격_브랜치_이름
```

### 원격 저장소 최신 메타데이터 갱신

```sh
git fetch
```

`git pull`은 원격 저장소의 내용을 가져와 로컬 코드에 즉시 병합하지만, `git fetch`는 원격의 최신 커밋 정보만 다운로드하고 로컬 작업 트리는 건드리지 않는다. 충돌 위험 없이 안전하게 원격 상황을 파악할 수 있다.

### 과거 커밋으로 롤백 및 원격 강제 반영

잘못 작성된 커밋을 제거하고 과거 시점으로 되돌릴 때는 `git reset`을 사용한다. 그중 `--hard` 옵션은 커밋 이력뿐만 아니라 워킹 디렉터리의 수정 파일까지 해당 시점으로 완전히 덮어쓰므로 각별한 주의가 필요하다.

```sh
# 현재 HEAD 기준 바로 1단계 이전 부모 커밋으로 롤백 (작업 내용 전부 폐기)
git reset --hard HEAD~1

# 특정 커밋 해시 시점으로 작업 트리와 히스토리를 완벽하게 되돌리기
git reset --hard 커밋해시코드

# 로컬에서 되돌린 과거 상태를 원격 저장소에 강제로 덮어쓰기 (주의 필요)
git push origin 브랜치이름 -f
```

`git push -f`(`--force`)는 원격 저장소의 히스토리를 로컬의 과거 시점으로 강제 재작성한다. 다른 팀원이 이미 해당 브랜치를 pull하여 작업 중인 경우 협업 환경에 치명적인 혼선을 초래할 수 있으므로, 단독 작업 브랜치가 아니라면 사용을 지양해야 한다.

## 결론 및 요약

Git의 고급 기능을 제대로 활용하면 버전 관리 중 발생하는 대부분의 예외 상황을 터미널에서 빠르고 정확하게 해결할 수 있다.

- **브랜치 변경 및 동기화**: 로컬 브랜치명을 `git branch -m`으로 바꾼 뒤, `git push -u`와 `--delete`로 원격 저장소의 연결을 재정비한다.
- **히스토리 추적과 복구**: 일반적인 커밋 검토는 `git log --oneline`과 `git show`를 활용하고, 커밋 유실 시에는 `git reflog`를 통해 과거 포인터를 찾는다.
- **롤백 시 안전 확보**: `git reset --hard`와 `git push -f`는 파괴적인 작업이므로, 사전에 `git fetch`와 로그 검토를 거친 후 신중하게 실행해야 한다.

저장소 관리가 꼬였을 때는 주저하지 말고 터미널을 열어 `git branch -vv` 명령어로 브랜치 추적 상태부터 먼저 점검해 볼 것을 권장한다.
